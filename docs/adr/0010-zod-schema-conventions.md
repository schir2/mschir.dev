# ADR 0010 — Zod Schema Conventions

## Status

Accepted

## Context

PrimeVue forms use Zod for validation via `@primevue/forms/resolvers/zod`. The naive pattern is to define a Zod schema, infer the TypeScript type from it (`z.infer<typeof Schema>`), and co-locate the resolver alongside the schema. This creates a second source of truth for types: one from Zod, one from Supabase-generated `database.types.ts`.

Early implementations (e.g. `useAuthCredentials.ts`) bundled the schema, inferred type, and resolver into a single composable file. This coupled a validation concern (Zod), a UI wiring concern (PrimeVue resolver), and a type definition into one place, and placed them in `composables/` where reactive state belongs.

## Decision

### Schema files live in `app/schemas/`

File naming: `<Domain>Schema.ts` — e.g. `CredentialsSchema.ts`, `ContactSchema.ts`.

### Schema files export the Zod schema only

No inferred types. No resolver. The file's single responsibility is the validation shape.

### Types are sourced from the type layer, not inferred from schemas

- **DB-backed types**: come from `shared/types/` (generated by Supabase). Schemas use `satisfies { [K in keyof T]: z.ZodTypeAny }` to prove the schema covers the shape.
- **Frontend-only types** (no DB table origin): defined in `app/types/` and referenced the same way.

Supabase-generated types are the authoritative source of truth for any shape that has a DB backing. Inferring the same type from Zod would create divergence risk.

### Resolvers live in the consuming component

`zodResolver(SomeSchema)` is PrimeVue-specific wiring. It belongs in the `<script setup>` of the component that owns the `<p-form>`, not in a shared file.

### Example

```ts
// app/schemas/CredentialsSchema.ts
import { z } from 'zod'
import type { Credentials } from '~/types/Credentials'

export const CredentialsSchema = z.object({
  email: z.string().min(3).email(),
  password: z.string().min(8),
} satisfies { [K in keyof Credentials]: z.ZodTypeAny })
```

```ts
// In the component
import { zodResolver } from '@primevue/forms/resolvers/zod'
import { CredentialsSchema } from '~/schemas/CredentialsSchema'
import type { Credentials } from '~/types/Credentials'

const resolver = zodResolver(CredentialsSchema)
```

## Consequences

- Supabase-generated types remain the single source of truth for DB-backed shapes.
- Schema files are portable and framework-agnostic — they do not import PrimeVue.
- The `satisfies` constraint catches schema/type divergence at compile time.
- Components carry one extra line (`zodResolver(...)`) but the intent is explicit at the point of use.
- No inline schemas in components or pages — every form's validation shape is locatable in `app/schemas/`.
