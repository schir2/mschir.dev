# shared/types/CLAUDE.md

Types here are available to both the Nuxt server layer and the client. Only put types here that could legitimately be consumed by server routes or middleware — i.e., types derived from Supabase table rows.

## File naming

- One file per Supabase table, named in **singular PascalCase** after the primary entity.
  - `Article.ts`, not `Articles.ts`
  - `Project.ts`, not `Projects.ts`
  - `ArticleSeries.ts`, `ArticleTag.ts`, `ArticleCategory.ts` — each gets its own file
- `database.types.ts` is auto-generated by Supabase; never edit it by hand.

## What belongs here

Each file owns:
1. The **table alias** for its primary entity: `export type Article = Database['public']['Tables']['articles']['Row']`
2. `Insert` and `Update` variants if the entity is written to from the app.
3. **Composite/view types** whose primary entity is that table (e.g. `ArticleCardItem`, `ArticleDetail`, `ArticleListItem` all live in `Article.ts`; `ArticleSeriesSummary` lives in `ArticleSeries.ts`).
4. **Domain enums or string unions** that are values of a column on that table (e.g. `WritingStage` lives in `Article.ts`).
5. **Shared Supabase select strings** used by two or more pages to fetch the same shape — export as a named `as const` constant co-located with the matching type (e.g. `ARTICLE_CARD_SELECT` lives next to `ArticleCardItem` in `Article.ts`). Ad-hoc select strings used in only one place stay local to that file.

Composite types that span multiple tables belong in the file of the **primary/driving table** — the one whose rows are being listed or detailed.

## What does NOT belong here

- Frontend-only types (composable parameter shapes, UI-specific types with no DB origin) → use `app/types/` instead.
- Unexported local types used only once in a single file → keep them local.
- Ad-hoc query shapes defined inline in components or pages → extract to the appropriate file here or in `app/types/`.
